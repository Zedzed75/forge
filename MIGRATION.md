## 2. Technical constraints discovered (copier 9.17.2 spike, validated)

These points were verified experimentally, not assumed. They condition the port
of the templates.

1. **File multiplicity**: copier's `yield` tag
   (`[% yield e from envs %][[ e.name ]][% endyield %]` in a *path name*)
   entirely replaces the legacy `planner.py`. **Yields nest**: a yield on a
   directory name and another on a file name inside it produce the cartesian
   product, the parent level's variable staying available
   (`inventories/<env>/host_vars/<host>.yml` generated by a single template). A
   single `yield` tag per path *segment*; forbidden in a file's *content*
   (`YieldTagInFileError`). A segment rendered empty is ignored → `[% if %]`
   serves as a file filter.
2. **Custom Jinja2 filters**: copier does not accept filters passed in Python,
   but `_jinja_extensions` loads an importable extension. The legacy filters are
   therefore ported into `forge.jinja_ext.ForgeExtension` (filters **and**
   globals work, verified).
3. **`copier update` requires a versioned template**: if `src_path` designates a
   subdirectory of a git repository, copier does **not** see it as a VCS
   template, does not write `_commit`, and the update fails ("cannot obtain old
   template references"). Validated workaround: `src_path` = **the forge
   repository root** + `_subdirectory: "src/forge/plugins/[[ plugin ]]/template"`
   in a single root `copier.yml`. `_commit` is then filled in and `copier update`
   three-way merges a template evolution with a manual edit (verified).
4. **Answers file**: copier only writes `.copier-answers.yml` if the template
   contains `[[ _copier_conf.answers_file ]].jinja`. That file is mandatory in
   every plugin template.
5. **Only the declared questions are recorded** in the answers, so only they
   survive an `update`. Any data passed to copier must correspond to a question
   declared in the root `copier.yml`.
6. **`vcs_ref`**: by default copier uses the **latest tag** and works on a
   *clone* — uncommitted template modifications are invisible. With
   `vcs_ref="HEAD"`, copier includes the dirty working tree
   (`DirtyLocalWarning`): that is the mode expected in development and for the
   golden tests.
7. **Windows / long paths**: path names carrying a `yield` tag are long;
   copier's temporary clone does not inherit `core.longpaths` and `git add`
   fails there ("Filename too long"). Validated workaround, **without touching
   the user's git configuration**: forge exports
   `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=core.longpaths GIT_CONFIG_VALUE_0=true`
   around its copier calls. The forge repository itself is configured with
   `core.longpaths=true`.
8. **`_src_path` is absolute** in the answers file: a generated project would
   otherwise be tied to the workstation that generated it. The core rewrites
   `_src_path` to the current template root before any `update`.
9. **No interactive prompt**: `defaults=True` is mandatory, otherwise copier
   opens a prompt and breaks under Git Bash (`NoConsoleScreenBufferError`).
10. **A render made from a dirty working tree is not "updatable"** (observed in
    phase 2). With `vcs_ref="HEAD"` and uncommitted modifications, copier creates
    a *temporary commit* in its throwaway clone and records it in `_commit`. That
    commit exists nowhere afterwards: `copier update` fails on
    `git checkout <sha>` → "pathspec did not match". Practical consequence:
    `forge generate` always works in development, but `forge update` requires a
    **committed** template (hence the `vX.Y.Z` tags of decision Q8). The core
    turns copier's raw failure into an explicit message, and the update test is
    skipped as long as the repository is dirty.
11. **`_src_path` must only be rewritten if it points elsewhere**: rewriting an
    equivalent value (different separators) dirties the target repository, and
    copier refuses to update a dirty repository.

### Arbitrations of the Helm port (phase 4, 2026-08-25)

The phase 1 audit said "port plus completion"; measurement confirms it and makes
it precise: **the legacy model is far ahead of its templates.**
`models/component.py` declares 9 addons and 12 sub-blocks, but
`templates/chart/` renders only two — `deployment` and `service`. The 32 files
of the parity snapshot therefore cover only a fraction of the model.

**Consequence for the nature of phase 4**: it is not an at-parity port like
phase 3. It is a **port of the model** (faithful and verifiable, parity defined
on the 32 files of the snapshot) **plus the creation of nine template families**
that have never existed. Those nine cannot be proven by parity: they are proven
by `helm lint`, `helm template` and `kubeconform -strict`, and by fresh golden
references.

Decisions taken, not to be reopened without a new reason:

| # | Point | Decision |
|---|---|---|
| H1 | **Two sources for the Ingress host**: the core brings `service.environments[].domain`, the legacy derives the host from `components[].ingress.base_domain` + `host_includes_env` | `service.environments[].domain` **wins** when it is filled in: the host becomes `<prefix>.<env-domain>`, **without** re-inserting the environment name (the domain already carries it). Fall back on `base_domain` otherwise. Neither of the snapshot's two specs has a `domain`: parity is preserved, and the core's field finally takes on a meaning. |
| H2 | **Two sources for "this environment is production"**: `service.environments[].production` (explicit boolean) vs recognition by NAME (`prod`, `prd`, `production`…) | `production: true` **forces** the prod profile (and `host_includes_env=false`). In its absence, recognition by name applies — it is what makes a minimal spec equivalent to a complete one, and MIGRATION §4 asks to keep it. An `Issue` at level **warning** is emitted when the two sources diverge, rather than silently deciding. |
| H3 | `layout: umbrella` declared in the enum but `NotImplementedError` in the planner, no template | **Removed from the enum.** Leaving an unimplemented value in an `extra="forbid"` schema is a trap for the user: they write it, it passes validation, and generation blows up. To be reintroduced with its templates. |
| H4 | `helm.environments`: a list of objects carrying their own `name` (legacy) or a dict keyed by name (DESIGN §3.1) | **Dict**, like `ansible.hosts.<env>` and `ansible.group_vars.<env>`. The name and the order now live in `service.environments`. Consequence: the "unknown environment key" cross-check becomes indispensable, exactly as in `ansible/answers.cross_check`. |
| H5 | `components[].port` (DESIGN §3) against `container_port` / `port_name` / `service.port` (legacy) | **The three legacy fields are kept.** Merging them would lose the nominal Helm case (Service:80 → container:8080) and the port name the probes pick up. `port` would be a false friend: DESIGN §3 is corrected. |
| H6 | Length caps (`service.name` ≤ 40, environment name ≤ 20, `description` ≤ 200) and `owner_email` format | Checked by the **Helm plugin's cross-check**, never by the core: these are constraints of `Chart.yaml` and of the 63-character budget of Kubernetes resource names. The core has no business knowing Helm. |
| H7 | Dead legacy fields (modelled, never read by a template) | **Kept**, those whose template arrives in phase 4: `create_namespace`, `secrets.*`, `persistence`, `hpa`, `pdb`, `config`, `secret`, `cron`, `networkpolicy`, `serviceaccount`, `ingress`. **Dropped**: `extras.helmfile` and `extras.ci` (no template planned, and CI is repository-level — decision Q6), `servicemonitor` (out of scope, MIGRATION §4). `extra="forbid"` will refuse them cleanly. |
| H8 | `extras.ci` (enum `none\|github\|gitlab`) against `ansible.options.write_ci` (boolean) | Two domains expressed the same thing in two ways. **Not ported.** If a Helm CI becomes necessary, it will align on the boolean form, or move up to the shared block. |
| H9 | The legacy Helm project-level `.gitignore` (it ignores `secrets.yaml`) | Becomes `helm/.gitignore`, like Ansible's `.gitignore`: every domain stays self-contained and deletable (decision Q6). |
| H10 | The `@spec` sentinel: the planner wrote a copy of the specification into the project | **Removed.** The unified specification is written by the core at the root of the target (parity divergence 3). |
| H11 | `validate_assignment=True` of the legacy `ForgeModel`, worked around by writes into `__dict__` | **Not reintroduced.** The derivations are computed in a pure `derive.py` that produces the `domain` dict directly, the pydantic spec staying immutable after validation — the only mode compatible with `.copier-answers.yml`. |
| H12 | The `KUBERNETES_VERSIONS` window (1.34, 1.35, 1.36) against DESIGN §3's `1.31` example | The model's window is authoritative; **DESIGN §3's example is corrected**. It is revalidated against the `kubeconform` actually installed, and not widened to make an example pass. |

Measured conversion pitfalls, specific to Helm:

- `comment` is called by **no** existing Helm template: the signature pitfall
  reported in §5 does not concern the port. On the other hand every **new** call
  written during the catalogue completion must name the width
  (`| comment(width=76)`), otherwise 76 would be read as an indentation.
- `yaml_value(4)` and the like are positional in the legacy templates, but the
  two implementations have the **same** signature: nothing to rename. The filter
  produces its own separator, hence the tag stuck to the colon — do not add a
  space when porting, that would create a trailing blank which the core no longer
  cleans up (divergence 10).
- `values.yaml.j2` and `values-env.yaml.j2` are dense with `[% if %]` blocks and
  loops with interleaved empty lines. The legacy engine collapsed multiple empty
  lines after rendering; the core no longer does. **The fix is in the template**,
  never in the core.
- `values_ref(name)` (from `engine/naming.py`) is indispensable: it renders
  `.Values.api` for a Go-compatible name, and `(index .Values "my-api")` for a
  name with a hyphen. Without it, a component named with a hyphen produces a
  chart that does not compile. To be exposed through
  `forge.plugins.helm.jinja_ext.GLOBALS`.

## 5. Duplicates to merge (debt avoided)

The two tools reimplemented the same thing; only one version must survive, in
the core. **Merge carried out in phase 2** — the "where" column indicates the
file that is now authoritative.

| # | Duplicate | Arbitration | Where |
|---|---|---|---|
| 1 | `ForgeModel` (`extra="forbid"`) | identical implementations, only one kept | `forge/spec/types.py` |
| 2 | `spec_io` (deterministic YAML) | the ansible-forge version (more complete), made domain-agnostic; the header now lists the domains present | `forge/spec/io.py` |
| 3 | Tool detection and installation message | merge of `verify.require_tools` + `validation.tools.require`, plus the WSL fallback | `forge/validate/tools.py` |
| 4 | Execution report | `Report`/`Check` (helm) kept, enriched with the `missing`, `skipped`, `timeout` states and the `stdin_from` chaining | `forge/validate/runner.py` |
| 5 | The `comment`, `yaml_scalar` filters | **arbitrated**: `yaml_scalar` = the ansible-forge version (accepts any scalar, identical rendering on strings); `comment` = the ansible-forge version (preserves the source indentation, renders empty lines as `#`) + helm-forge's `prefix` parameter. Signature `comment(text, indent=0, width=88, prefix="# ")`: **the helm templates that passed the width in 2nd position must name it** (`\| comment(width=76)`) — to be applied in phase 4. | `forge/jinja_ext.py` |
| 6 | Output normalisation | **union rejected after verification**: the core limits itself to CRLF → LF and to a single trailing newline; `.copier-answers.yml` is spared (copier's internal write). See the box below. | `forge/render/copier_runner.normalise_text` |

> **Why the "union" of the two legacy normalisations was abandoned.**
> The migration plan intended to combine ansible-forge's per-line `rstrip` and
> helm-forge's collapsing of multiple empty lines. Measured in phase 2: these two
> transformations **are not neutral**. In a YAML scalar quoted over several lines,
> an empty line encodes a literal newline — collapsing them changes the value read
> back (`'para1\n\npara2'` becomes `'para1\npara2'`). In a `|` block, trailing
> spaces are part of the data. Applied blindly after rendering, they therefore
> modified the delivered content without saying so, and the golden references —
> blessed *after* normalisation — ratified the corruption instead of detecting it.
> Cleaning up the blanks left by `[% if %]` blocks is the template's business
> (`trim_blocks` / `lstrip_blocks`, active in the root `copier.yml`): verified, the
> `demo` plugin's output contains neither a trailing space nor a surplus empty
> line, with no post-processing at all. The core, for its part, cannot know what
> carries meaning in a file — that is exactly the kind of knowledge it is not
> allowed to have. **Consequence for phases 3 and 4:** if a ported template leaves
> blanks, the fix is in the template, never in the core.

Filters also brought together in `forge/jinja_ext.py` without divergence:
`yaml_assign`, `lower_first`, `rule` (ansible-forge) and `to_yaml`, `yaml_value`,
`indent_block` (helm-forge). `camel` stays with the Helm plugin; `j()`/`jstr()`
are removed (decision Q1). A plugin adds its own filters through a
`<plugin-package>.jinja_ext` module exposing `FILTERS`/`GLOBALS`, loaded by
`ForgeExtension`: **the root copier.yml is never edited for a domain**.

### State of the Helm port (phase 4, 2026-08-25)

**Parity reached: 32 files identical byte for byte** on the two cases of
`tests/parity/helm/`, apart from the divergences above.

**And completion: nine resource families created** — ingress, configmap,
statefulset, cronjob, secret, hpa, pdb, serviceaccount + RBAC, networkpolicy.
The legacy model declared them all; none had a template.

The point of method that made the thing verifiable: the two parity
specifications declare `addons: [service]` and `addons: []`, so **none** of the
nine addons. The completion was therefore written to be **totally inert** to
them — every block is rendered only if its addon is present. Parity did not have
to be degraded to make room for the new: it stayed at 32/32 throughout the work,
and the nine families are proven separately by `tests/golden/helm-complet/`, by
`helm lint`, `helm template` and `kubeconform -strict`.

Five defects found **by the completion itself**, corrected:

1. **A StatefulSet without its headless Service.** The model forced
   `service.headless = true` but not the addon: the Service was therefore not
   generated, and `serviceName` designated a non-existent resource — the
   StatefulSet lost the stable network identity that is its only reason to
   exist. No validator could see it, the manifest remaining valid.
2. **`rbac.create` and `rbac.rules` hardcoded in `values.yaml`**, hence
   unreachable from `forge.yml` and lost at every regeneration. An `rbac` block
   was added to the component model, with validation of the rules (the API
   refuses a rule without `verbs`; `kubeconform` lets it through).
3. **`port_name` without a constraint.** Kubernetes imposes the IANA_SVC_NAME
   format (15 characters); a 29-character name passes `helm lint`,
   `helm template` **and** `kubeconform -strict`, and is only refused at apply
   time.
4. **A HorizontalPodAutoscaler with no metric at all** was generated when no
   resource reservation was declared. Valid against the schema, it would never
   have acted — a mute autoscaler is more misleading than no autoscaler.
5. **`helm.environments.<env>.extra_values` was rendered nowhere**: the user's
   free-form values disappeared silently. A gap inherited from the legacy,
   corrected here.

## Closing the port (phase 10, 2026-08-26)

**`_legacy/` is removed**, along with `tests/parity/`, its two test modules and
its harness. This document is what remains of the original tools.

### Divergences 12 to 15 are lifted

They formed a single batch — outdated mentions of `ansible-forge` and
`helm-forge` in the generated READMEs, kept alive by the parity constraint alone.
They were corrected **in one block**, and the golden snapshot re-blessed in the
same commit, as planned:

| Divergence | Was | Is |
| --- | --- | --- |
| 12 | `ansible-forge generate --spec forge.yml [--output . --force]` | `forge generate --only ansible [--force]`, and the pointer to `forge update --only ansible`, which does not lose the modifications |
| 13 | `helm-forge generate --spec forge.yml` | `forge generate --only helm`, same pointer |
| 14 | `forge generate --force` presented as a non-existent flag | the flag **exists**; the divergence was outdated, the command is now `forge generate --only helm --force` |
| 15 | the Helm README's tree listed `forge.yml` under `helm/` | the tree shows only `helm/`, and a sentence says where the specification really lives |

**Two mentions are kept, and that is not an oversight**:
`ssh_hardening_dropin_file: 99-ansible-forge.conf` and
`users_sudoers_file: 90-ansible-forge`. These are not documentary mentions but
**names of files dropped on the managed machines**. Renaming them would leave the
old file in place on every already-managed host: two contradictory SSH drop-ins,
or two sudoers files, with nothing to signal it. The template now carries that
explanation as a comment, at the place where the question comes up.

### Why parity stops

It was measuring a resemblance to tools that no longer exist, and the generated
project had outgrown it as early as phase 4:

- the Helm chart has **nine resource families** the original tool never had —
  its model declared them, no template rendered them;
- the Ansible project passes **`ansible-lint` in production profile**, which the
  original suite had never verified: its only test on that was skipped.

Non-regression is now held by `tests/golden/` alone, which compares byte for
byte, and by the real validators of each domain.

### What the port left the project

The pattern used twice — **freeze a snapshot, convert, loop until zero
divergence** — was of no use to the two domains written from scratch, which had
no snapshot. It is the real validators that played that role there, and they
found what no parity would have seen: `tflint` reported a variable declared and
never used, `promtool` showed that frozen test series proved nothing as soon as
the threshold changed.
