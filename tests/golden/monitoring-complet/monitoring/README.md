# Monitoring — boutique

Boutique en ligne, supervision

Owner: Equipe Plateforme (plateforme@example.net)
> Project generated by forge. Do not edit it by hand: modify `forge.yml` at the
> root, then `forge generate`. To receive only the evolutions of the template
> without losing your modifications, `forge update --only monitoring`.

## What this project watches

- **`availability`** — The target no longer answers the collector
- **`error_rate`** — Too many responses in server error *(requires: the application itself (Prometheus client))*
- **`latency`** — The service answers too slowly *(requires: the application itself (Prometheus client))*
- **`saturation`** — Consumption close to the limits (memory, CPU) *(requires: cAdvisor, exposed by the kubelet)*
- **`restarts`** — A container is restarting in a loop *(requires: kube-state-metrics)*
- **`probe`** — External probe: reachability and certificate expiry *(requires: blackbox exporter)*

The complete catalogue, with the traps of each family, is consulted through
`forge catalog monitoring` and `forge catalog monitoring <family>`.

## What makes these alerts checkable

Every alert comes with a **unit test** played by `promtool test rules`: a
synthetic time series is built, the rule is evaluated at a given instant, and the
test checks that the alert appears with the right labels and the right
annotations.

This is the only check that bears on **meaning**. A rule can be syntactically
faultless and never fire: non-existent metric name, misspelled label, comparison
on the wrong side of the threshold. Neither `promtool check rules` nor
`promtool check config` sees it — and nobody notices before the day the alert
should have gone off.

This is **not an option**: the tests are generated in every case. Making them
optional would have invited the wrong choice.

## Environments

| Environment | Namespace watched | Targets collected | External probes |
| --- | --- | --- | --- |
| `dev` | `boutique-dev` | 1 | 1 |
| `prod` **(production)** | `boutique-prod` | 2 | 1 |

One configuration per environment, and not a single shared one: the thresholds
differ, and so does the namespace watched.

### Thresholds applied

| Threshold | dev | prod | 
| --- | --- | --- | 
| `certificate_days` | 21 | 30 | 
| `cpu_cores` | 1.5 | 3 | 
| `error_rate` | 0.2 | 0.02 | 
| `latency_p95_seconds` | 2 | 0.8 | 
| `memory_ratio` | 0.9 | 0.85 | 
| `restarts_per_hour` | 3 | 2 | 

They are set per environment in `forge.yml`, under
`monitoring.environments.<env>.thresholds`.

## Checking

With `make`:

```bash
make check ENV=dev   # configuration, rules, tests
make all                                  # all three, on every environment
```

Without `make`, or for one precise command:

```bash
promtool check config prometheus/dev/prometheus.yml
promtool check rules  prometheus/dev/rules/*.yml
promtool test rules   tests/dev/*.yml
```

`forge validate` chains exactly these commands on every environment.

## What this project does not do

- **It does not deploy Prometheus.** It produces its configuration and its rules;
  installing the collector, Grafana and the exporters is up to you.
- **It does not route the alerts.** Alertmanager is not configured here: its
  configuration cannot be validated offline by any tool shipped with Prometheus,
  and forge only generates what it can have checked. The `severity`, `service`
  and `env` labels carried by every alert are what a routing needs.
- **It does not discover the targets.** They are written in the configuration. A
  target never declared produces no series, and therefore no alert: silence is not
  health. If your targets change often, replace `static_configs` with
  `file_sd_configs` or with a Kubernetes discovery.
- **The dashboard is not validated by a tool.** `grafana/dashboards/boutique.json` is a
  well-formed JSON whose structure forge checks, but no offline Grafana linter
  exists: the guarantee is weaker there than on the rules. Import it and look at
  it.
