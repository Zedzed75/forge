# Terraform module "storefront"

Online store, infrastructure foundation

> File generated by forge. Do not edit it by hand: modify `forge.yml` at the root
> of the project, then run `forge generate` again — or `forge update` to receive
> only the evolutions of the template.

This module sets up **the base** the service is deployed on: the partition, its
budget, the identity that deploys there. It does **not** deploy the application
workload — that is the role of a Helm chart, which targets the namespace this
module exposes as an output.

It configures no provider: it is the calling root (`environments/<env>/`) that
decides which cluster is targeted. The module therefore stays callable from any
root.

## Resource families retained

### `namespace` — Creates the namespace the service is deployed in

Sets up the partition itself, with the app.kubernetes.io labels of the service. This is the pivot family: the others attach themselves to it by reference, which gives Terraform the creation order with no explicit depends_on.

Absent, the module assumes the namespace already created by the platform team and merely attaches itself to it by its name.

Sets up: `kubernetes_namespace`.

Points to watch:

- `terraform destroy` deletes the namespace, and therefore **everything** it contains -- including what a Helm chart deployed there and that Terraform does not know about. The destruction goes beyond the perimeter.
- Changing the name of the namespace destroys and recreates it (ForceNew behaviour): the content is lost, with no warning other than the plan line.
- A namespace being deleted stays in the Terminating phase as long as a finalizer has not given back control; Terraform waits, and the wait looks like a hang.

### `quota` — ResourceQuota and LimitRange: the budget of the namespace

Caps what the namespace can consume and gives a default size to the containers that do not declare one.

This is the family that has the most effect on the other domains: as soon as a ResourceQuota covers cpu or memory, the API refuses any pod whose container has no `resources.requests`.

Sets up: `kubernetes_resource_quota`, `kubernetes_limit_range`.

Points to watch:

- As soon as a quota covers `requests.cpu` or `requests.memory`, **every** pod without `resources.requests` is refused at admission. The Helm chart of the same service must therefore declare its requests, otherwise the deployment breaks the day the quota is set up.
- The LimitRange only applies to the pods **created after** it: the pods already in place keep their configuration, and the divergence is only seen at the next restart.
- A quota reduced below the current consumption evicts nothing: it only blocks the subsequent creations. The namespace looks healthy until the next deployment.

### `registry_secret` — Image pull secret for a private registry

Sets up a `kubernetes.io/dockerconfigjson` Secret that the pods reference in `imagePullSecrets`. The credentials are **never** written in the specification nor in the generated files: they arrive through TF_VAR_registry_password.

Sets up: `kubernetes_secret`.

Points to watch:

- The key of the Secret must be exactly `.dockerconfigjson`, leading dot included, and the value a complete `{"auths": {...}}` document. A bare `auths` key is accepted by Terraform and rejected by kubelet on the first pull.
- The provider encodes `data` in base64 itself; passing an already encoded value there double-encodes it silently. It is `data`, not `binary_data`, that receives plain text.
- The `auth` field of the document is the `user:password` pair in base64 -- an encoding, not an encryption. Anyone who reads the Terraform state or the Secret reads the password.
- An imagePullSecret only applies in its namespace: a service deployed in several namespaces needs one Secret per namespace.

### `service_account` — ServiceAccount, Role and RoleBinding for the deployments

Gives the deployment chain an identity of its own in the namespace, with the rights strictly necessary to a `helm upgrade`: read and write the application objects, nothing more. No cluster-scoped right is granted.

Sets up: `kubernetes_service_account`, `kubernetes_role`, `kubernetes_role_binding`.

Points to watch:

- Since Kubernetes 1.24, no token Secret is created automatically for a ServiceAccount: `default_secret_name` is empty. A durable token requires a `kubernetes.io/service-account-token` Secret declared explicitly -- prefer a short-lived token obtained through `kubectl create token`.
- In a RoleBinding `subject`, a ServiceAccount wants `api_group = ""`; it is `rbac.authorization.k8s.io` that holds for a User or a Group. The opposite is accepted by Terraform and rejected by the API at apply time.
- A Role only applies in its namespace. The cluster-scoped objects -- CustomResourceDefinition, StorageClass -- will stay inaccessible, which is intended.

### `network_policy` — Closes the namespace by default, and reopens the strict minimum

Sets up a deny-by-default policy on the whole namespace, then reopens that without which nothing works: DNS resolution, and the incoming traffic coming from the namespace of the ingress controller.

Without a network plugin that applies them (Calico, Cilium, Antrea), a NetworkPolicy is accepted by the API and **without any effect**: the namespace looks protected and is not.

Sets up: `kubernetes_network_policy`.

Points to watch:

- A deny-by-default policy with no egress rule towards DNS (port 53, UDP **and** TCP) breaks all name resolution in the namespace. The outage presents itself as application slowness, not as a network problem.
- An empty `pod_selector {}` selects **every** pod of the namespace. That is exactly what is wanted for a deny-by-default, and exactly what is not wanted in an opening rule.
- In a `from` rule, `namespace_selector` and `pod_selector` in the **same** block form an AND; in two separate blocks, an OR. The difference between the two is a far wider opening than intended, and nothing reports it.
- The kubelet probes come from the node, not from a pod: an ingress rule that is too strict makes the probes fail and restarts the service in a loop.

### `random_secret` — Generated passwords, deposited as a Secret

Generates one password per requested key and deposits them in a single Secret. No secret value enters forge.yml nor any generated file: that is the point of the family.

Sets up: `random_password`, `kubernetes_secret`.

Points to watch:

- `random_password` keeps the value **in plain text in the Terraform state**. The state backend must therefore be encrypted and its access restricted: the password is no more secret than the state.
- Without `keepers`, the value never changes -- which is the intended behaviour, but forbids any rotation. Rotating a password requires modifying a keeper, not destroying the resource.
- `random_password` produces by default special characters that break connection URLs (`@`, `/`, `:`). Hence the restricted `override_special` in the generated code.
- The service that reads this Secret does not reread it on its own: a Secret mounted as a volume is refreshed with a delay, a Secret injected as an environment variable is **never** refreshed before a restart.

### `tls_certificate` — Self-signed certificate of the working environments

Builds a private key and a self-signed certificate, deposited as a `kubernetes.io/tls` Secret ready to be referenced by an Ingress.

**For working environments only.** In production, a self-signed certificate is refused by any serious client: use cert-manager or a certificate issued by a recognised authority. The generated code recalls it in a comment.

Sets up: `tls_private_key`, `tls_self_signed_cert`, `kubernetes_secret`.

Points to watch:

- The certificate expires without reporting anything: Terraform only regenerates it on the next apply, and only if `early_renewal_hours` is reached. A project applied twice a year with a one-year certificate breaks down.
- The private key is stored **in plain text in the state**, like any resource of the tls provider.
- Browsers have ignored the Common Name since 2017: a certificate without `dns_names` matching the host is refused, whatever its CN.
- A `kubernetes.io/tls` Secret requires exactly the two keys `tls.crt` and `tls.key`. Any other naming is accepted by the API and ignored by the ingress controller.

## What this module does not do

- **It does not deploy the application.** The namespace it exposes is meant to
  receive a Helm chart or a manifest; the two meet on the name of the namespace,
  and on nothing else.
- **It manages no real secret.** The secret values arrive through
  `TF_VAR_<name>`; those it generates itself live in the Terraform state, which
  must therefore be encrypted.
- **It grants no cluster-wide right.** A `Role` only applies in its namespace, and
  that is deliberate.
